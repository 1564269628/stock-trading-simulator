# Stock Trading Simulator

一个可解释的股票模拟交易系统：Vue 3 前端、TypeScript、Vite、Node.js、Express 和 WebSocket。所有用户、订单、订单簿、持仓、资金和成交记录都保存在服务端内存中，重启后会重置。

## 启动

```bash
npm install
npm run dev
```

打开 http://localhost:5173。服务端运行在 http://localhost:3000，健康检查为 `/api/health`。

### Docker 启动

需要已安装 Docker Desktop / Docker Engine 和 Docker Compose。

部分网络环境下，Docker Compose 构建阶段访问 Docker Hub 可能失败。建议先拉取基础镜像：

```bash
docker pull node:22-alpine
```

然后构建并启动：

```bash
docker compose up --build
```

启动后访问：

```text
http://localhost:5173
```

停止并清理容器：

```bash
docker compose down
```

Docker 仅用于本题的一键本地运行与复现；运行时数据仍保存在服务端内存中，容器重启后会重置。

## 功能

- 本地注册与登录
- 3 支模拟股票，每秒随机行情更新
- BUY / SELL 限价单
- 价格优先、时间优先、部分成交
- 成交后的资金、持仓和成交记录更新
- REST 命令与初始快照、WebSocket 实时事件
- WebSocket 断线后自动重连；重连成功后重新请求 `/api/state`，用完整快照同步最新委托、持仓、成交、行情历史和盘口
- WebSocket 意外断线后固定 1 秒自动重连，并重新请求 `/api/state` 恢复最新业务状态
- 浏览器页面因网络切换被重新加载时，会使用本地保存的 userId 自动恢复登录状态；暂时断网不会要求重新登录。只有服务端内存中已不存在该用户（例如服务重启）时才返回登录页

## 结构

```text
apps/server/src/
  store.ts             # 内存状态
  matchingEngine.ts    # 独立撮合核心
  tradingService.ts    # 下单与成交记账
  routes.ts            # REST API
  websocketHub.ts      # 实时推送
  marketSimulator.ts   # 行情模拟
apps/web/src/
  App.vue              # 单页界面
  services/            # REST 与 WebSocket 客户端
```

新订单主动吃对手盘：买单匹配最低卖价，卖单匹配最高买价；同价按递增 sequence 保证时间优先；成交价使用已在订单簿中的 resting order 价格。资金和持仓只在成交后记账，活动 BUY/SELL 分别占用购买力与持仓 reservation，不实现生产级认证。

## 关键架构决策

### 1. 撮合、行情和价格语义解耦

系统中明确区分 `referencePrice`、`Trade.price` 和 `latestPrice`：

- `referencePrice`：模拟的市场参考价，每秒小幅随机变化，主要用于 Bot 在合理价格附近生成订单；
- `Trade.price`：真实成交价格，由撮合引擎产生；
- `latestPrice`：最近一笔真实成交的价格；
- 随机行情本身不会直接修改真实成交价。

真实撮合始终遵循价格优先、时间优先；买价大于等于卖价时才成交，**成交价等于先进入订单簿的对手方订单价格**。

例如先挂 `SELL 1111 × 50`，后来提交 `BUY 1500 × 50`，最终以 1111 成交，而不是使用随机参考价重新计算成交价格。这样将“模拟市场变化”和“真实交易结果”彻底分开。

### 2. 引入 Bot 提供市场流动性，但 Bot 也走真实交易流程

如果只有一个真实用户操作，往往没有另一侧订单，订单可能长期无法成交，五档盘口、最新价和成交记录也难以持续变化。因此引入 3 个系统 Bot，模拟其他市场参与者持续提供买卖订单，而不是直接伪造成交。

最终 Bot 策略保持简单：

- 每 1 秒对三只股票分别生成订单；
- 每只股票随机生成 2～4 笔买单和 2～4 笔卖单；
- 数量从 `10 / 20 / 50 / 100` 中随机；
- 价格在当前 `referencePrice` 附近约 ±0.5% 随机产生；
- 未成交 Bot 订单约 9 秒后自动撤销，避免订单簿无限堆积；
- 五档盘口直接从真实活动订单簿聚合得到。

最重要的是，Bot 和真实用户共用同一条交易链路：

```text
Bot / 用户生成订单
        ↓
    submitOrder
        ↓
   TradingService
        ↓
   MatchingEngine
        ↓
真实 OrderBook / Trade
```

Bot 不能直接写入成交记录，也不维护第二套“假盘口”。因此页面上的盘口、成交记录和最新价都来自同一个真实订单簿和同一个撮合引擎。

### 3. 挂单占用购买力和持仓，只有真实成交后才真正结算

只检查当前 `cash` 会产生重复使用资金的问题：例如用户有 100 万现金，连续挂两笔各 80 万且尚未成交的买单，如果第二笔仍只看账户里的 100 万，两笔都会被接受，之后都成交时现金可能变成负数。

因此系统使用“预留额度”而不是下单即扣款：

```text
可用资金
= 账户现金
- 所有活动 BUY 的 (委托价格 × 剩余数量)

可卖数量
= 实际持仓
- 所有活动 SELL 的剩余数量
```

PENDING / PARTIALLY_FILLED 订单占用额度，FILLED / CANCELLED 不再占用。下单时不真正扣现金和持仓；只有发生真实 `Trade` 后才按实际成交价和成交数量结算，撤单后剩余部分的占用自动释放。

例如 `BUY 1500 × 100` 会按 1500 × 100 占用最大购买力，但如果最终以 1111 × 100 成交，账户实际只扣 1111 × 100。

## AI 协作记录

### Prompt 1：用 Harness 把 AI 开发变成“计划—实现—审查—修复”的闭环

**场景 / 问题：** Research 阶段完成需求和架构以后，需要让 Codex 正式开发。如果只说“帮我把项目做完”，AI 容易一次修改大量文件，而且测试通过也不代表实现真的符合需求。

**代表性 Prompt：**

> 使用 Harness 接手股票模拟交易系统。先阅读需求、架构、实现计划和 AI 协作文档，不要直接开始写代码。从最新 main 创建独立实现分支，先写 Implementation Plan，再按照 Task 分阶段实现。每个 Task 完成后运行对应测试，不扩大需求。实现完成以后不要直接合并，再使用独立 Reviewer 对照需求、Implementation Plan 和实际代码进行 Review；Reviewer 只提出问题，不修改代码。发现问题后交回 Codex 定向修复，再重新 Review，直到问题闭环。

**AI 回复后的调整：** 第一轮实现后，Review 又发现 REST 测试覆盖不完整、Harness 目录索引没有更新、集成测试不足和 Vue 源码补丁残留等问题。我没有直接合并，而是持续执行“计划 → 实现 → 独立审查 → 定向修复 → 再审查 → 最终验收”。

### Prompt 2：从真实成交异常反推规则，纠正 AI 的成交价设计

**场景 / 问题：** 人工测试时，我先以 1111 挂出卖单，随后另一个用户以 1500 买入，但页面显示成交均价约为 1478.18。实现虽然能成交，但成交规则已经偏离预期。

**代表性 Prompt：**

> 我是 1111 先卖的，然后另一个人 1500 来买，为什么成交均价是 1478.18？谁先挂在订单簿里，就按照谁的限价成交。1111 的卖单已经在订单簿里，后来 1500 的买单进来应该按 1111 成交。随机行情和参考价不能修改真实成交价，价格优先、时间优先保持不变。不要为了处理极端订单修改核心成交规则，极端订单是另外的问题。

**AI 回复后的调整：** AI 曾尝试用参考价、买方限价和卖方限价之间的限制值解决极端价格问题，但这改变了核心撮合语义。我明确否定该方案，最终恢复为“成交价 = 对手方已挂订单的价格”，并增加价格优先、时间优先、resting price、部分成交和多档成交测试。

### Prompt 3：重新定义“最新价”，纠正随机行情和真实成交混在一起的问题

**场景 / 问题：** 第二阶段人工测试时发现，页面顶部最新价、图表最后价格和刚发生的真实成交价可能不同。继续检查发现，最初设计让随机行情每秒直接修改 `latestPrice`，导致同一个字段同时表示“随机行情价”和“最近真实成交价”。

**代表性 Prompt：**

> 这个问题不是简单的页面显示错误，而是价格的含义没有统一。最新价应该表示最近一笔真实成交价格，而不是后台随机生成的价格。请把几个价格职责拆开：`referencePrice` 只用于模拟市场中心和 Bot 报价；`Trade.price` 由真实撮合产生；`latestPrice` 等于最近一笔真实 `Trade.price`。不要修改已经确定的 resting order 成交规则，也不要在前端再维护第二份最新价。

**AI 回复后的调整：** 最终将数据流改成“随机市场变化 → referencePrice → Bot 附近生成订单 → 真实撮合 → Trade.price → latestPrice → 页面 / 图表”，随机行情不再直接覆盖真实成交价格。

### Prompt 4：为了提供市场流动性引入 Bot，发现方案过度复杂后主动做减法

**场景 / 问题：** 本地模拟系统通常只有一个用户操作，没有另一侧订单时很难持续成交。为了解决这个问题，需要 Bot 模拟其他市场参与者。但 AI 第一版为了长期维持固定五档盘口，设计了专门挂单 Bot、专门吃单 Bot、固定五档、成交后自动补档以及参考价变化后重挂订单等机制，明显超过了题目需要。

**代表性 Prompt：**

> 这个方案太复杂了。不要区分专门挂单 Bot 和专门吃单 Bot，也不要强制维护固定五档、自动补档、重新调整已有挂单。Bot 的目的只是模拟其他市场参与者，持续产生正常买卖订单。简化为每秒对三只股票分别随机生成几笔买单和卖单，价格围绕参考价小幅随机，数量随机；Bot 和用户全部调用同一个 `submitOrder`，进入同一个撮合引擎；五档盘口直接从真实订单簿取前五档；长时间没有成交的 Bot 订单自动撤销。不要再写第二套撮合逻辑，也不要维护假的五档盘口。

**AI 回复后的调整：** 最终删除复杂的专用做市逻辑，改为每秒对每只股票随机产生 2～4 笔 BUY 和 2～4 笔 SELL，统一进入正常撮合；Bot 老挂单约 9 秒后撤销，盘口只聚合真实订单簿的最优五档。这里的关键不是让 AI 多做，而是发现过度设计后主动缩小方案。

### Prompt 5：发现“余额够一笔，但不够多笔挂单”后，引入购买力和持仓预留

**场景 / 问题：** 最初 BUY 只判断“当前现金是否够这一笔订单”。例如 100 万现金先挂一笔 80 万 BUY，现金尚未真正扣除，再挂第二笔 80 万时如果仍只看当前 cash，两笔都会通过，之后都成交就可能出现负余额；卖单也会重复使用同一批持仓。

**代表性 Prompt：**

> 不能只检查当前 cash。已经挂在订单簿里的 BUY 虽然还没有真正成交，但已经占用了购买力。可用资金应该是 `cash - 所有未完成 BUY 的 price × remainingQuantity`，新 BUY 再用自己的 `price × quantity` 与可用资金比较。卖单同样处理，未完成 SELL 要占用对应持仓。但不要在下单时真正扣现金或持仓，只有发生 Trade 时才按实际成交价结算；如果订单撤销，剩余部分占用自动释放。Bot 也必须遵守同样规则。

**AI 回复后的调整：** 最终区分了“账户实际余额”和“当前可用购买力”，以及“实际持仓”和“可卖持仓”。活动订单占用额度，真正账户结算仍严格依据 `Trade.price × Trade.quantity`。

AI 生成的代码不会替代人工验收；最终以自动化测试、构建结果和真实业务流程验证为准。

# 第二阶段交易体验

当前实现包含 600519 贵州茅台、000858 五粮液、300750 宁德时代，支持交易终端式股票切换、独立 BUY/SELL、最多 90 个价格历史点的 SVG 实时折线图、5 档派生盘口和普通 Bot 流动性。

状态快照明确区分 `marketTrades`（全市场最近成交）和 `myTrades`（当前用户实际参与的成交）；交易工作区按当前选中股票过滤委托、成交、持仓和盘口。

卖出订单由服务端校验：可卖数量等于当前持仓减去同股票未成交卖单的 remainingQuantity。Bot 与普通用户共用 `submitOrder -> MatchingEngine`，不直接创建成交或修改订单簿。

验证命令：

```bash
npm test
npm run build
npm run dev
```

### 模拟行情与 Bot 流动性

每只股票都有独立的后台参考价，每秒小幅随机游走。Bot 围绕参考价通过正常订单与撮合引擎提供流动性；用户仍可提交任意合法的正数限价。页面最新价只来自真实成交，成交价按已在订单簿中的 resting order 价格执行。

### Task 6D 模拟市场

后台参考价每秒变化；Bot 对三只股票每秒随机提交 2~4 笔 BUY 和 2~4 笔 SELL，价格约在参考价 ±0.5%，全部经过统一撮合引擎。未成交 Bot 订单约 9 秒自动撤销，用户订单可通过“取消”按钮撤销剩余部分。页面展示真实订单簿最优 5 档，成交价按已在订单簿中的 resting order 价格执行。

### Task 6E 交易信息展示

“我的订单”保留当前股票的完整订单历史，包括 PENDING、PARTIALLY_FILLED、FILLED、CANCELLED，并基于真实成交显示成交量、均价和金额。市场成交按股票分别显示最新 20 条，最新记录在前。卖出表单只展示当前持仓，服务端仍执行完整的 SELL 超卖校验。

### Task 6F 现金购买力与时间

活动 BUY 按委托价乘剩余数量占用购买力，资金不足时整笔拒绝；挂单不直接扣现金，只有真实成交才按成交金额结算，取消后释放剩余购买力。服务端保存 ISO 时间，前端统一显示本地 `YYYY-MM-DD HH:mm:ss`。
