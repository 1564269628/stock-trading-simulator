# 股票模拟交易系统需求分析

> 状态：Research 阶段  
> 原则：严格依据编程题，只收敛需求，不实现业务代码。

## 1. 项目目标

实现一个简单、完整、可解释的股票模拟交易 Web 应用。

本题重点不是堆技术，而是证明能够在 AI 协作下完成：

- 需求拆解；
- 合理的代码组织；
- 限价单撮合逻辑；
- 前后端与实时通信闭环；
- 测试与问题定位；
- 对 AI 产出的审查和解释。

因此本项目优先级是：

1. 正确；
2. 简单；
3. 可测试；
4. 面试时能讲清楚；
5. 再考虑附加挑战。

## 2. 固定技术栈

按题目和本次约束固定为：

- 前端：Vue 3
- 前端语言：TypeScript
- 构建工具：Vite
- 后端：Node.js
- Web 框架：Express
- 实时通信：WebSocket
- 数据存储：全部使用 Node.js 进程内存

不引入数据库、Redis、消息队列或微服务。

## 3. 必做功能

### 3.1 登录 / 注册

- 支持本地模拟注册。
- 支持本地模拟登录。
- 用户数据保存在服务端内存。
- 不要求数据库。
- 不实现生产级认证体系。

登录成功后，前端保存当前会话所需的最小用户标识，用于查询该用户的订单、资金和持仓。

### 3.2 行情看板

至少提供 3 支模拟股票，每支展示：

- 股票代码；
- 股票名称；
- 最新价；
- 涨跌幅。

行情规则：

- 服务端每秒对股票价格进行一次随机小幅波动；
- 最新行情通过 WebSocket 推送到前端；
- 随机行情仅用于行情看板，不自动生成买卖订单，不直接参与订单撮合。

### 3.3 交易面板

用户可以：

- 选择股票；
- 输入限价；
- 输入数量；
- 提交买入委托；
- 提交卖出委托。

最小输入校验：

- 股票代码必须存在；
- 方向必须为 BUY 或 SELL；
- 价格必须大于 0；
- 数量必须为正整数。

### 3.4 委托列表

每笔委托至少包含：

- 订单 ID；
- 用户 ID；
- 股票代码；
- 买卖方向；
- 限价；
- 原始数量；
- 剩余数量；
- 状态；
- 创建时间；
- 用于严格时间优先的内部顺序号。

订单状态建议保持最小集合：

- PENDING：未成交；
- PARTIALLY_FILLED：部分成交；
- FILLED：完全成交。

前端：

- “未成交”展示 PENDING 和 PARTIALLY_FILLED；
- “已成交”展示 FILLED。

题目未要求撤单，因此 MVP 不实现 CANCELLED 和撤单接口。

## 4. 撮合规则

仅支持限价单。

### 4.1 价格优先

买单：

- 买价越高，优先级越高。

卖单：

- 卖价越低，优先级越高。

### 4.2 时间优先

同一价格下：

- 越早进入订单簿的订单越先成交。

为避免多个订单落在同一毫秒导致时间比较不稳定，内部使用单调递增 sequence 作为最终时间优先依据；创建时间主要用于展示。

### 4.3 成交条件

最高买价 >= 最低卖价时可以成交。

即：

- incoming BUY 可以与 ask.price <= buy.price 的卖单成交；
- incoming SELL 可以与 bid.price >= sell.price 的买单成交。

### 4.4 部分成交

每次成交数量：

`min(买单剩余数量, 卖单剩余数量)`

如果一方成交完：

- 状态变为 FILLED；
- 从活动订单簿移除。

如果一方仍有剩余：

- 状态变为 PARTIALLY_FILLED；
- 继续参与后续撮合。

### 4.5 成交价约定

题目规定了“价格优先、时间优先”，但没有明确交叉后的成交价。

本项目采用一个简单且确定的实现约定：

- **成交价取订单簿中已存在的对手方订单价格，即 resting order / maker price。**

例如：

- 已有卖单 10 元；
- 新买单限价 11 元；
- 成交价为 10 元。

这样容易解释，也不会额外设计复杂定价规则。

## 5. 资金与持仓

每个新用户：

- 初始资金固定为 1,000,000 虚拟币。

每次成交后：

- 买方资金减少：成交价 × 成交数量；
- 买方对应股票持仓增加；
- 卖方资金增加；
- 卖方对应股票持仓减少。

### 5.1 题目未定义的账户风控

题目没有明确要求：

- 下买单时冻结资金；
- 下卖单时冻结持仓；
- 禁止余额不足；
- 禁止卖空；
- 初始持仓如何产生；
- 保证金规则。

如果自行实现完整资金 / 持仓冻结，会明显扩大需求。

因此 MVP 将“资金和持仓”定位为**成交后的模拟记账结果**，不把证券风控作为本题验收目标。

这意味着实现阶段不额外构建冻结资产系统。如果后续决定增加“禁止卖空”等规则，需要先明确初始持仓来源，再作为单独需求处理。

## 6. 成交记录

每笔成交至少记录：

- tradeId；
- 股票代码；
- 成交价格；
- 成交数量；
- 买单 ID；
- 卖单 ID；
- 买方用户 ID；
- 卖方用户 ID；
- 成交时间。

前端展示最近成交记录。

## 7. 实时通信

必须使用 WebSocket 推送：

- 行情变化；
- 用户委托变化；
- 用户资金 / 持仓变化；
- 成交变化。

职责划分：

- REST API：注册、登录、初始状态读取、提交订单；
- WebSocket：后续实时状态变化推送。

WebSocket 断线自动重连属于题目附加挑战，不作为第一阶段完成标准。

## 8. 数据存储

以下数据全部保存在后端内存：

- 用户；
- 股票行情；
- 订单；
- 买卖订单簿；
- 用户持仓；
- 用户资金；
- 成交记录。

服务重启后数据丢失，符合题目要求。

## 9. 明确不做

为了严格控制范围，MVP 不实现：

- MySQL / PostgreSQL 等数据库；
- Redis；
- 消息队列；
- 微服务；
- 真实证券行情；
- 市价单；
- 撤单；
- 订单修改；
- K 线；
- 五档盘口等复杂行情 UI；
- 涨跌停；
- 手续费；
- 交易时段；
- 复杂风控；
- JWT / OAuth；
- 权限系统；
- 多实例部署；
- 分布式一致性。

Docker 和 WebSocket 自动重连只作为时间允许时的附加挑战。

## 10. 验收标准

### 10.1 基础功能

- 可以注册和登录；
- 至少展示 3 支股票；
- 行情每秒小幅变化；
- 页面能够实时收到行情；
- 可以提交买入 / 卖出限价单；
- 可以查看当前用户委托；
- 可以查看资金与持仓；
- 可以查看最近成交记录。

### 10.2 撮合引擎

自动化测试至少覆盖：

1. 买单价格优先；
2. 卖单价格优先；
3. 同价时间优先；
4. 部分成交；
5. 一笔订单连续匹配多笔对手订单；
6. 价格没有交叉时不成交；
7. 成交后订单状态和剩余数量正确；
8. 成交后资金和持仓按成交价、成交数量正确更新。

### 10.3 工程可复现性

最终目标：

- 根目录执行一次 `npm install` 安装前后端依赖；
- 根目录执行一次 `npm run dev` 同时启动前后端；
- README 能让面试官在几分钟内跑起来。

## 11. Research 阶段结论

本项目规模小，不需要为了展示 Harness 而过度设计。

Research 阶段只输出：

- 需求边界；
- 架构设计；
- Implementation Plan；
- AI 协作记录规范。

不写业务代码。

后续建议使用一个 Implementation PR 完成 MVP，并在该 PR 中按计划分阶段实现、测试和审查。
# 第二阶段补充

交易体验升级增加中国股票展示、独立买卖面板、有限价格历史、派生盘口和模拟 Bot。SELL 不允许卖出当前持仓减活动卖单占用后的可卖数量；该规则由服务端最终执行。

最新价语义：没有真实成交时保持不变；真实成交后等于该股票最后一笔成交价。行情 tick 只广播当前价，不单独随机改写价格。
## Task 6C 价格与流动性

- 系统为每只股票维护独立 `referencePrice`，每秒小幅随机游走。
- 用户限价不受参考价范围限制；SELL 仍受持仓约束。
- Bot 每秒围绕参考价提供普通限价流动性，并只主动撮合参考价 ±2% 内的 resting order。
- 真实 `Trade.price` 仍由 resting-order price 决定，`latestPrice` 仍等于该股票最近真实成交价。
## Task 6D 随机订单与撤单

- Bot 每秒对每只股票随机生成 2~4 笔 BUY 与 2~4 笔 SELL，数量为 10/20/50/100，价格约在 `referencePrice ±0.5%`。
- Bot 与用户统一经过 `submitOrder -> MatchingEngine`；未成交订单进入真实订单簿。
- 真实盘口按 asks 升序、bids 降序聚合并展示前 5 档，不强制填满。
- Bot 活动订单约 9 秒未完全成交自动取消；用户可取消 PENDING/PARTIALLY_FILLED 剩余部分。
- 成交价为 `clamp(referencePrice, sellLimit, buyLimit)`，`latestPrice` 仍只来自真实成交。
## Task 6E 展示规则

- 我的订单包含当前股票的全部订单状态，取消后的部分成交订单仍保留真实成交摘要。
- 市场成交按股票分别保留/返回最新 20 条，前端按时间倒序展示。
- SELL UI 不显示可卖数量；服务端 `availableToSell` 和 SELL reservation 继续阻止超卖。
## Task 6F 现金与时间规则

- `availableCash = cash - Σ(active BUY price × remainingQuantity)`，活动 BUY 仅为 PENDING/PARTIALLY_FILLED。
- 资金不足的 BUY 在创建订单前整笔拒绝；挂单不直接扣 cash，真实成交按 Trade 金额扣款。
- CANCELLED/FILLED BUY 不再占用购买力；SELL 继续使用持仓 reservation。
- 服务端保留 ISO 时间，前端统一按本地 `YYYY-MM-DD HH:mm:ss` 展示。
